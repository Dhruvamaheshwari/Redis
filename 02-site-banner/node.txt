REDIS LEARNING PROJECT - 02 SITE BANNER NOTES
===============================================

Purpose
-------
This folder contains a small Express API that stores and manages a site banner message in Redis.

The example teaches the basic Redis commands SET, GET, DEL, and EXISTS through HTTP endpoints.

Project files
-------------
- package.json: Project metadata, scripts, and npm dependencies.
- package-lock.json: Locked dependency versions generated by npm.
- src/index.js: Express server, Redis client, banner key, and API routes.
- node_modules/: Installed npm packages. This is generated and should normally not be committed.

Technologies
------------
- Node.js
- Express 5
- ioredis 6
- Redis 6 package is listed as a dependency, but the current source uses ioredis.

How the application works
-------------------------
1. The Node.js process creates an Express server.
2. express.json() parses JSON request bodies.
3. ioredis connects to Redis using Redis_url, or redis://localhost:6379 by default.
4. Every banner operation uses the Redis key app:banner.
5. The API can create/update, read, delete, and check the existence of the banner.
6. The API listens on PORT, or port 3000 when PORT is not set.

Redis key
---------
Key: app:banner

The value is a text message. The key is shared by all requests to this running Redis instance.
Because no expiration is configured, the value remains until the key is deleted or Redis data is cleared.

API endpoints
-------------
POST http://localhost:3000/banner

Request body:
{"message":"Welcome to our website"}

Behavior:
- Saves the message with Redis SET.
- If message is missing or empty, saves Welcome to chai aur Redis.

Response:
{"succ":true}

GET http://localhost:3000/banner

Behavior:
- Reads the banner with Redis GET.

Response when a banner exists:
{"message":"Welcome to our website"}

Response when no banner exists:
{"message":null}

DELETE http://localhost:3000/banner

Behavior:
- Removes app:banner with Redis DEL.

Response:
{"succ":true}

GET http://localhost:3000/banner/health

Behavior:
- Checks the key with Redis EXISTS.

Response when the key exists:
{"health":true}

Response when the key does not exist:
{"health":false}

Prerequisites
-------------
- Node.js and npm
- A running Redis server on localhost:6379, or a custom Redis URL
- The Redis service from folder 01 can be started with Docker Compose:
  cd ..\01
  docker compose up -d

Install dependencies
--------------------
From this folder, run:

npm install

Start the API
-------------
From this folder, run:

npm run dev

The server should listen on:

http://localhost:3000

Test with PowerShell
--------------------
Create or update a banner:

Invoke-RestMethod -Method Post -Uri http://localhost:3000/banner -ContentType "application/json" -Body '{"message":"Redis learning banner"}'

Read the banner:

Invoke-RestMethod http://localhost:3000/banner

Check banner health:

Invoke-RestMethod http://localhost:3000/banner/health

Delete the banner:

Invoke-RestMethod -Method Delete http://localhost:3000/banner

Environment variables
---------------------
Redis_url
- Optional.
- Exact variable name currently used by src/index.js, including the capital R.
- Default: redis://localhost:6379
- Example: redis://localhost:6379

PORT
- Optional.
- Default: 3000
- Example: 3500

PowerShell example:

$env:Redis_url = "redis://localhost:6379"
$env:PORT = "3000"
npm run dev

Redis command mapping
---------------------
- POST /banner -> SET app:banner <message>
- GET /banner -> GET app:banner
- DELETE /banner -> DEL app:banner
- GET /banner/health -> EXISTS app:banner

Common problems
---------------
- Connection refused: start Redis and verify port 6379 is available.
- Wrong environment variable: use Redis_url exactly as written by the current source code.
- Empty response: the banner key may not exist; POST a message first.
- Port already in use: choose another port with the PORT environment variable.
- Redis value remains after restarting Node.js: Redis stores the key separately from the Node process.

Learning ideas
--------------
- Add a TTL with SETEX or EXPIRE.
- Validate that message is a non-empty string.
- Return proper HTTP status codes for invalid input and Redis failures.
- Add a cache-control or version field to the stored value.
- Use a Redis hash for multiple site settings.
- Add graceful shutdown with redis.quit().
- Add error handling around every Redis operation.
- Add automated tests for all four endpoints.
- Rename Redis_url to the conventional REDIS_URL and update the code consistently.

Important reminder
------------------
This is a local learning project. Do not expose an unauthenticated Redis server or this API publicly without authentication, validation, network restrictions, and production error handling.
